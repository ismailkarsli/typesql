# @typesql/prisma

Use your Prisma schema as a TypeSQL schema, and run TypeSQL queries through Prisma Client's
raw query API. There are two ways to get the `DB` type that `createSql` expects:

- **The `typesql-prisma` generator** (recommended). Add it to `schema.prisma`; every
  `prisma generate` writes a `DB` interface with the real database names (`@map`, `@@map`),
  native types (`@db.*`), database defaults, enums and `@@schema` namespaces.
- **`FromPrisma<Prisma.TypeMap>`**, a type-level conversion of the client Prisma already
  generates. No extra generator, but Prisma's generated types do not record database names,
  native types or schemas, so those come from Prisma's defaults unless you add overrides.

```sh
npm install @typesql/prisma @typesql/core
```

## The generator

```prisma
generator client {
  provider = "prisma-client"
  output   = "../src/generated/prisma"
}

generator typesql {
  provider = "typesql-prisma"
  output   = "../src/db/typesql.ts"
}
```

`npx prisma generate` then writes:

```ts
// src/db/typesql.ts
// Generated by @typesql/prisma from the Prisma schema. Do not edit.
import type { Col, Nullable, Generated, NullableGenerated, View } from "@typesql/core";

export interface DB {
  /** Prisma model `User`. */
  users: {
    id: Generated<"int4">;
    email: Col<"varchar">;
    /** Prisma field `name`. */
    display_name: Nullable<"text">;
    role: Generated<"Role">;
    tags: Nullable<"text[]">;
    /** `@updatedAt`: set by Prisma Client, no database default. */
    updatedAt: Col<"timestamp">;
  };
  auth: {
    accounts: { /* ... */ };
  };
  $types: {
    Role: "ADMIN" | "USER" | "guest";
  };
}
```

```ts
import { createSql } from "@typesql/prisma";
import type { DB } from "./db/typesql";

const sql = createSql<DB>(prisma);
const rows = await sql("SELECT id, display_name FROM users WHERE email = $1", email).execute();
// { id: number; display_name: string | null }[]
```

Options in the generator block:

| Option | Default | |
|---|---|---|
| `output` | required | a `.ts` file, or a directory (the file is then `index.ts`); relative to the schema file |
| `typeName` | `"DB"` | name of the exported interface |
| `importFrom` | `"@typesql/core"` | module the `Col`/`Nullable`/... helpers are imported from |

Prisma runs the provider as a shell command from the directory you run `prisma` in, so
`typesql-prisma` is found when Prisma is started through `npx`, `pnpm exec`, `yarn` or a
package script (which put `node_modules/.bin` on the `PATH`). Otherwise use
`provider = "node node_modules/@typesql/prisma/dist/bin.js"`.

### What the generator emits

| Prisma | TypeSQL |
|---|---|
| `model User` / `@@map("users")` | `DB["User"]` / `DB["users"]`: the table name |
| `name String? @map("display_name")` | column `display_name` |
| `@@schema("auth")` (multiSchema) | `DB["auth"]["accounts"]`; `public` (or no `@@schema`) stays at the top level |
| `view ActiveUser { ... }` | `View<{ ... }>`: readable, rejected as an `INSERT`/`UPDATE`/`DELETE` target |
| `field T?` | `Nullable<...>` |
| `field T[]` | `Nullable<"t[]">`: Prisma creates scalar lists without `NOT NULL` |
| `@default(autoincrement())`, `@default(now())`, `@default(dbgenerated(...))`, `@default(sequence())`, literal defaults (`@default(0)`, `@default(USER)`, `@default([])`) | `Generated<...>`: the column has a database `DEFAULT` |
| `@default(uuid())`, `@default(cuid())`, `@default(nanoid())`, `@default(ulid())`, `@updatedAt` | **no** default: Prisma Client fills these in; raw `INSERT`s must supply them |
| `enum Role { GUEST @map("guest") }` / `@@map("role")` | `$types`, keyed by the database name, with the database values (`"guest"`) |
| relation fields | skipped (the foreign-key scalar fields are columns) |
| `Unsupported("...")` fields | not emitted: Prisma leaves them out of the DMMF |
| `///` documentation comments | copied to the generated doc comments |

Postgres types (`@db.*` wins over the scalar default):

| Prisma scalar | default | `@db.*` |
|---|---|---|
| `String` | `text` | `Text` → `text`, `VarChar` → `varchar`, `Char` → `bpchar`, `Uuid` → `uuid`, `Citext` → `text`, `Inet` → `inet`, `Xml` → `xml`, `Bit` → `bit`, `VarBit` → `varbit` |
| `Int` | `int4` | `Integer` → `int4`, `SmallInt` → `int2`, `Oid` → `oid` |
| `BigInt` | `int8` | `BigInt` → `int8` |
| `Float` | `float8` | `DoublePrecision` → `float8`, `Real` → `float4` |
| `Decimal` | `numeric` | `Decimal` → `numeric`, `Money` → `money` |
| `Boolean` | `bool` | `Boolean` → `bool` |
| `DateTime` | `timestamp` (`timestamp(3)`, no time zone) | `Timestamp` → `timestamp`, `Timestamptz` → `timestamptz`, `Date` → `date`, `Time` → `time`, `Timetz` → `timetz` |
| `Json` | `jsonb` | `Json` → `json`, `JsonB` → `jsonb` |
| `Bytes` | `bytea` | `ByteA` → `bytea` |

Length, precision and scale arguments (`VarChar(200)`, `Decimal(10, 2)`) are dropped:
TypeSQL types columns by type name only.

The generator speaks Prisma's generator protocol itself (no `@prisma/generator-helper`).
`@typesql/prisma/generator` exports `generateSource(datamodel, options)`, which turns a DMMF
datamodel into the source text the generator writes.

## `FromPrisma`: converting the generated client's types

```ts
import { createSql } from "@typesql/prisma";
import type { Prisma } from "./generated/prisma/client";

const sql = createSql<Prisma.TypeMap>(prisma);
// same as createSql<FromPrisma<Prisma.TypeMap>>(prisma)

sql('SELECT id, email, "createdAt" FROM "User" WHERE role = $1', "ADMIN");
// Query<{ id: number; email: string; createdAt: Date }, ["ADMIN" | "USER"]>
```

`Prisma.TypeMap` is exported by the generated client. Tables are keyed by **model name** and
columns by **field name**, with types from the scalar defaults in the table above. Enums go
to `$types` under their Prisma name. Relation fields are skipped; views (no create
operations) become `View<...>`.

| Read from | For |
|---|---|
| `<Model>FieldRefs` (`FieldRef<"User", "Int">`) | the columns and their Prisma types |
| `<Model>OrderByWithRelationInput` (`SortOrderInput` is offered for nullable fields) | nullability |
| `<Model>CreateManyInput` (optional fields) | has a default |
| the scalars payload (`$Enums.Role`) | enum values |

### Overrides

What Prisma's types do not record can be supplied per model and field:

```ts
import type { FromPrisma } from "@typesql/prisma";

type DB = FromPrisma<Prisma.TypeMap, {
  User: {
    $table: "users";                       // @@map("users")
    name: { column: "display_name" };      // @map("display_name")
    email: "varchar";                      // @db.VarChar(200): shorthand for { type: "varchar" }
    updatedAt: { default: false };         // @updatedAt has no database default
  };
  Account: { $schema: "auth"; createdAt: "timestamptz" };   // @@schema("auth") → DB["auth"]["Account"]
  $types: { Role: "ADMIN" | "USER" | "guest" };             // @map'ped enum values
}>;
```

| Model key | |
|---|---|
| `$table` | table name |
| `$schema` | Postgres schema; anything but `"public"` nests the table under `DB[schema]` |
| `<field>` | a Postgres type name, or `{ column?, type?, nullable?, default? }` |

For list fields `type` is the element type (`tags: "varchar"` → `varchar[]`). Unknown model,
field and option names are compile errors. Enum types keep their Prisma name.

### Limitations of `FromPrisma`

- **Names.** Without overrides, table and column names are the model and field names. Postgres
  folds unquoted identifiers to lower case, so a model `User` and a field `createdAt` must be
  quoted in SQL: `SELECT "createdAt" FROM "User"`. `SELECT createdAt FROM User` is an error,
  as it would be in Postgres.
- **Defaults.** A field is "has a default" when it is optional in Prisma's create input. That
  includes client-side defaults (`uuid()`, `cuid()`, `nanoid()`, `ulid()`) and `@updatedAt`,
  which have no database default: a raw `INSERT` that omits them type-checks but fails. Mark
  them `{ default: false }`, or use the generator.
- **Native types** (`@db.*`): `DateTime` is always `timestamp` (Prisma's default is
  `timestamp(3)` without time zone), `String` is `text`, and so on. Pin the others with overrides.
- **Enums** keep their Prisma name and values; `@map`'ped values and `@@map`'ped enum names need
  the generator (or `$types` overrides for the values).
- `Unsupported("...")` fields are not in Prisma Client's types.

## Running queries through Prisma

`createSql<DB>(prisma)` uses `PrismaTypeMap`, which describes what `$queryRaw` returns, and runs
the queries through Prisma Client: `execute*` with `$queryRawUnsafe(text, ...values)` and
`executeCount` with `$executeRawUnsafe(text, ...values)`. Despite the name, values are always
sent as bind parameters (`$1`, `$2`, ...), never spliced into the text. `prisma` is a
`PrismaClient`, an extended client or a transaction client.

`sql.transaction(fn)` runs `fn` in an interactive `prisma.$transaction(fn)`, with `tx` bound to
the transaction client; inside one, `tx.transaction(fn)` uses a savepoint.

```ts
import { createSql } from "@typesql/prisma";

const sql = createSql<DB>(prisma);

const [rows, deleted] = await sql.transaction(async (tx) => [
  await tx('SELECT id, "bigNum" FROM "User" WHERE id = $1', 1).execute(), // { id: number; bigNum: bigint }[]
  await tx("DELETE FROM posts WHERE author_id = $1", 1).executeCount(),   // number
]);
```

| Export | |
|---|---|
| `createSql<S, TM = PrismaTypeMap>(prisma)` | core's `createSql` with the queries running on `prisma` |
| `q.execute()`, `q.executeTakeFirst()`, `q.executeTakeFirstOrThrow()`, `q.executeCount()` | `Promise<Row[]>`, `Promise<Row \| undefined>`, `Promise<Row>` (`NoResultError` on 0 rows), `Promise<number>` |
| `sql.transaction(fn)` | `prisma.$transaction(fn)` with `tx` bound to the transaction client |
| `executor(prisma)` | an `Executor` for `q.execute(executor)` and core's `createSql(executor)`, e.g. with `{ rowKeys: "camelCase" }` |
| `PrismaSql<S, TM>`, `PrismaRawClient` | the type `createSql` returns, and what it accepts |

### `PrismaTypeMap`

Verified against `@prisma/adapter-pg` 7.10, Prisma's raw result serialization
(`client-engine-runtime`) and `@prisma/client`'s `deserializeRawResult`:

| Postgres | TS |
|---|---|
| `int2`, `int4`, `float4`, `float8` | `number` |
| `int8`, `oid` | `bigint` (so `count(*)` is `bigint`) |
| `numeric`, `money` | `Decimal` (`money` without the currency symbol) |
| `date`, `timestamp`, `timestamptz` | `Date` (`timestamp` is read as UTC) |
| `time`, `timetz` | `Date` on 1970-01-01 UTC |
| `bytea` | `Uint8Array` |
| `json`, `jsonb` | `JsonValue` |
| `bool` | `boolean` |
| `text`, `varchar`, `bpchar`, `name`, `uuid`, `xml`, `inet`, `cidr`, `bit`, `varbit` | `string` |
| enums and other user-defined types (`citext`, ...) | `string` (enums: their values) |

Arrays map element-wise. The other Postgres types (`interval`, `macaddr`, geometric types,
`tsvector`, ranges, `regclass`, `record`, ...) make Prisma throw "Unsupported column type"; they
are `unknown` here, and need a cast in SQL (`duration::text`). Arrays of enums and other
user-defined types arrive as the raw `{a,b}` text: cast them (`roles::text[]`).

To run the queries with another driver instead, use that adapter's `createSql<DB>(client)` with
the generated `DB` (`@typesql/pg` on the pool behind `@prisma/adapter-pg`, say).
